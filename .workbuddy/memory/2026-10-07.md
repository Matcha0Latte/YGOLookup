# 2026-10-07

## YGOLookup — Phase 0~3 完成

从空仓库起建「游戏王智能卡牌检索系统」，四个阶段全部落地并逐阶段 commit。

### 技术选型与关键决策

- 运行时**只用 Python 标准库**（sqlite3 / dataclasses / argparse），仅 dev 依赖 pytest。venv 在 `.venv/`。
- **SQLite 是唯一事实库**。`card_id` 为系统内部主键，外部 id 全部放 `external_id` 表（`ygopro_passcode` / `ygoprodeck_id`）。
- 双数据源：`ingest/ygopro/cdb_reader.py`（原生 cards.cdb）+ `ingest/ygopro/ygoprodeck.py`（JSON）。真实 `cards.cdb` 无公开直链镜像，故实际导入源是 YGOProDeck API；cdb 读取器用合成的 cdb 做了端到端测试。
- 迁移：`db/migrations/NNN_*.sql` + 自写的 forward-only runner（`db/migrations.py`）。001 建 card 层，002 建 effect 层。
- Effect 分层：`effect`（segment）+ `effect_predicate`（结构化谓词），`payload_json` 存完整对象，列只是镜像便于索引。
- **三值语义**：`action IS NULL` = UNKNOWN，`action_known` 0/1；`Tri` 枚举用于 tuner / once_per_turn。绝不把 parser 失败当成「卡片没有该效果」。
- Query AST（`query/dsl.py`）纯 JSON，与存储解耦；`retrieval/structured/compiler.py` 负责 AST → 参数化 SQL。

### 踩到的坑（重要）

- **扁平 EXISTS 连接极慢**：`effect JOIN effect_predicate WHERE e.card_id = c.card_id` 在 14.6k 卡上要 **68s**；改成嵌套 `EXISTS(effect WHERE card_id=... AND EXISTS(predicate WHERE effect_id=...))` 后 **0.1s**。原因：相关约束要先于谓词过滤生效。大批量重建后跑 `ANALYZE`。
- migration 001 里 `CREATE TABLE schema_migrations` 会与 runner 预建的那张冲突 → 改成 `CREATE TABLE IF NOT EXISTS`。
- 测试里 `connect()` 开的连接才带 `PRAGMA foreign_keys=ON`，裸 `sqlite3.connect` 默认关闭，测外键约束必须用项目 helper。
- splitter 不能在 `;` 处分句——PSCT 用 `;` 分隔 cost 与 resolution，切了就丢结构。只在 `.` 后接大写时切。
- 「2 Level 4 monsters」这类**素材行**要单独标 `marker=MATERIAL`，否则 parser 会编造无意义谓词。
- 激活子句（"Target 1 Spell/Trap on the field; destroy that target."）不是 COST：检测不到 action 时应作为 activation context 合并进 resolution 的 target；合并数值区间时要防止出现 min>max 的矛盾。
- `target_card_category` 存 `SPELL_TRAP` 单一 token，查询 `SPELL` 要展开成 `IN ('SPELL','SPELL_TRAP')`，反向不成立。

## 用户问答 + docs 中文化（commit `f83f09c`）

### 中文数据源调研结论（重要，已修正）

- 库里**完全无中文**：`card_name` 只有 14,597 条 `en / official`，`text_lang` 全 `en`。
- YGOProDeck API 的 `language` 参数**只支持 fr / de / it / pt**，传 `zh` 直接报错，这条路不通。
- **我第一次判断错了**：以为 ygocdb 只有按名搜索的单条端点。**实际有批量端点 `https://ygocdb.com/api/v0/cards.zip`**（2.4MB zip，内含单个 `cards.json` 13.77MB，14,342 条记录，1.6 秒下载完）。教训：先读完整 API 文档再下结论。
- `cards.zip.md5` 返回的 md5 **对应内层 cards.json，不是 zip 文件本身**（实测 json md5 = 082fc1aa…，zip md5 = 73e87bbe…）。做变更检测时要用解包后的 json 算 md5。
- 记录结构（dict，key 为官方 cid）：`cid` / `id`（8 位密码）/ `cn_name` / `sc_name` / `md_name` / `nwbbs_n` / `cnocg_n` / `jp_ruby` / `jp_name` / `en_name` / `text.{types,pdesc,desc}` / `data.{ot,setcode,type,atk,def,level,race,attribute}`。
- `text.types` 是结构化中文：「`[怪兽|通常] 龙/光\n[★8] 3000/2500`」——可直接解析出种族/属性/等级/ATK/DEF。
- `text.pdesc` 是**单独的灵摆效果文本**，天然对应我们的 `scope=PENDULUM` 分段。
- 覆盖度：14,342 条中 44 条 `id=0`（无密码，只能靠 cid/名字对齐）。按密码匹配我们 14,597 张卡 → **命中 14,237（97.5%）**。缺的 360 张里 124 SKILL + 106 TOKEN（ygocdb 不收），真正缺中文的只有约 130 张。
- 中文效果文本用 **① ② ③ 编号**，不是 `●`。现有 splitter 只认 `●` 和行首关键词，**接中文必须新增「圈号」marker**。
- 名称变体：`sc_name`（简中官方，可能为 None）vs `cn_name`（中文通用名）差异 12,288 条；另有 `md_name`（Master Duel 译名）。选哪个做 `canonical_name` 需用户定。

### 语言策略评估（英文 / 中文 / 日文）—— 待用户确认

**关键实测数据（决定了结论）**：

- 英文 `;` 出现于 **7,361 / 14,597 张卡（50.4%）**，这是我们切 COST / RESOLUTION 的唯一可靠分隔符。
- 中文 `；` 只出现在 **31 / 14,342 张（0.2%）**。中文表达 COST 用「才能发动」句式（**8,907 张，62%**），且 condition 与 cost 常混在同一句（"自己场上有怪兽存在的场合才能发动"）。
- 中文分段标记是 **① 9,756 张 / ：9,936 张 / 。14,218 张**，而 `●` 只有 1,148 张 —— splitter 接中文必须新增「圈号」marker，`●` 规则基本用不上。
- 中文 desc 平均 108 字、最长 286 字；14,298 条全有中文文本。
- **`sc_name`（简中官方名）只有 8,087 条（56%）；sc_name 为空但 desc 非空的有 6,217 条** → 中文效果文本覆盖远超简中官方发行范围，属社区（NW）翻译，非官方权威源。
- **ygocdb 完全没有日文效果文本**（`text` 只有 `types` / `pdesc` / `desc` 三个中文键），只有 `jp_name` / `jp_ruby`。换日文需另找源（Konami 官方 DB 爬取或日文 cdb）。

**我的推荐（四层分离）**：

1. 枚举 key 保留英文（`BANISH` / `GRAVEYARD`）——是机器标识，不是展示文案；挂在 ontology 上的中文 label + 同义词表供 LLM 映射与 UI 展示。
2. 解析源保留英文 PSCT——PSCT 是唯一为机器设计的卡面文本格式；中文丢掉了 `;` 分隔符，日文无空格且非 PSCT。
3. 中文做「检索入口 + 展示层」：中文名 / 中文全文 / 中文词表映射。
4. 日文只在 Phase 8 裁定层按需取原文，不进主链路。

**连带待办**：中文词表→enum key 的映射要收成单一可测数据源（现散落在 `query/planner.py`）；FTS5 的 trigram 分词器有 3 字符下限，「除外」「龙族」这类 2 字词会失效，Phase 4 必须先解决中文分词。

## 中文三级效果管道落地（commit `d9035a8` → `cad966e` → `9353f36`）

用户最终拍板：**直接解析简体中文，不先翻译成英文；中文是源语言，英文枚举是机器协议。**
数据来源以 ygocdb 为准。

### 管道

```
card_text(lang='zh') → EffectUnit → Clause → Predicate → effect_unit / effect_clause / effect_predicate
```

- `effects/units.py`：按 ①②③ + 全角冒号切 unit；kind = NUMBERED / UNNUMBERED / MATERIAL / RESTRICTION。
- `effects/clauses.py`：以「发动」为锚点，之前是 CONDITION/COST/TARGET/RESTRICTION，之后是 RESOLUTION。
  **「才能发动」不足以判定 COST** —— 「自己场上没有怪兽存在的场合才能发动」是 CONDITION。
  判定顺序 RESTRICTION → TARGET → COST（含可支付动作）→ CONDITION → UNKNOWN。
- `effects/predicates.py`：一个 clause 可产多个 predicate。中文宾语在动词**前面**，
  所以切片从上一个动作结束处开始；再按逗号把两端收窄，否则两个动作会共享名词短语。
- `effects/lexicon.py` + `effects/ontology.py` 是中文词表唯一来源，parser 模块不得出现中文字面量。
- `effects/extractors.py`：LLM 槽位，`LlmExtractor.extract()` 返回 None（v1 刻意留空）。

### 三个实测坑（都已在代码里修掉并有回归测试）

1. **最长匹配优先**。中文词表互相包含：「海龙族」含「龙族」、「兽战士族」含「兽族」、
   「魔法·陷阱卡」含「陷阱卡」。按插入顺序匹配会把海龙误判成龙族。→ `_longest_first()`。
2. **引号内卡名必须 mask**。「青眼白龙」不能产出 race=DRAGON。→ `mask_quoted()`。
3. **否定不是断言**。「这张卡不能通常召唤」若记成 NORMAL_SUMMON 会把语义反过来。
   → `is_negated()` + `modifiers["negated_action"]`。
